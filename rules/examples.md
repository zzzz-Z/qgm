# 规则

## 零、总则（最高优先级）

每次只生成可运行的脚本和当前脚本的功能，其他一概不输出。

**脚本首行必须写明作用**：生成的每个脚本，第一行必须是 `// @desc: <一句话说明本脚本做什么>`。执行时该注释会被读取，作为该次运行的会话记录摘要。

## 一、输出形状（ADHD 友好）

读者注意力有限，输出必须可直接行动。

1. **首行是动作**：命令 / 路径 / 片段放最前，背景放后面或删掉
2. **多步编号**：每步一个动作，能合并就合并，最少步骤优先


4. **不 recap**：不写「我已完成 X/Y/Z」，直接给下一动作
5. **不客套**：禁「好问题」「让我来」「希望能帮到你」「还有什么」
6. **报错就事论事**：写「文件:行号 - 现象 - 修法」，禁「哎呀」「似乎有问题」
7. **列表 ≤5 项**：超了拆「现在做 / 稍后做」
8. **不写旁支**：发现第二个问题，先做完当前，最后单独问一句

**例外**（以下覆盖上述规则）：

<!-- - 用户说「详细解释」→ 全展开，带标题，但无前言无结尾 -->

- 破坏性操作（`rm -rf` / 强制推送 / 迁移）→ 先确认
- 连续 3 轮「还是坏的」→ 停改代码，问一个诊断问题
- 用户选项类问题 → 给 2–4 个排序选项 + 一行取舍，推荐在前；**默认直接采用排第一的推荐方案**，不等用户确认（除非涉及破坏性操作或 §零 总则例外）；用户反对再切换

## 二、决策方式（懒 → 高效）

写任何代码前，从第一级阶梯往下试，命中即停：

1. 需要做吗？（YAGNI）
2. 项目里已有吗？复用
3. 标准库能做吗？
4. 平台特性覆盖吗？
5. 已装依赖能解吗？
6. 能一行吗？
7. 以上都不行，写最少能跑的

**规则**：

- 不引入未要求的抽象
- 删优于加，无聊优于聪明，文件越少越好
- 最短 diff 胜，但前提是真懂问题——不懂就改是造第二个 bug
- 修根因：grep 所有调用方，改共享函数一次；只修 ticket 提到的那条路径会漏掉兄弟调用
- 边界情况取正确算法，别取省事的脆弱算法
- 有意简化标 `ponytail:` 注释，写清上限和升级路径

**不偷懒**：理解问题（通读 + 追完整流程）、信任边界校验、防数据丢失的错误处理、安全、无障碍、真实硬件标定、用户明确要求的事。

**非平凡逻辑留一个可跑的 check**（assert 自检或一个测试文件），一行代码不用测。

## 三、项目约束

**文件改动必须走脚本**：任何增 / 删 / 改项目文件（源码、配置、资源），一律生成脚本执行，不手动编辑、不口头描述改法、不输出整文件让用户手动复制粘贴。脚本须满足下方必备能力（幂等 / 备份 / 回滚 / 自检）。例外：只读查询、纯解释、用户明确说「直接改」。

**脚本必备能力**（所有走脚本的改动都必须满足）：

- 幂等：重复跑安全
- 备份到 `.ai-runner/backup/`，镜像源路径，已存在保留
- `--rollback` 或独立回滚脚本
- 自检：关键结果逐条校验，失败 `process.exit(1)`
- 有色输出，非 TTY 自动去色
- 仅 TTY 下清屏
- 路径用 `path.join(ROOT, ...)`，不拼字符串

**输出规范**：

```
▶ 阶段
✓ 成功（绿）
! 跳过（黄）
⚠ 警告（黄）
✗ 失败（红，stderr）
▶ 下一步
```

用语义函数（`ok` / `skip` / `warn` / `err`），不裸打印。

**失败时报出文件 + 行号 + 现象**，可直接 grep。

**执行反馈格式**：

```
[脚本输出]
（原样贴）

[验证结果]
1 xxx：✓ / ✗（描述）

[报错]
（完整贴）
```

<!-- 出脚本时必须配套：验证清单（编号 + 操作 + 期望）、验证方式（命令行 / Console / 手动，选最直接的）、异常排查（具体命令或观察点）。 -->

收到反馈后：先诊断根因，最小修复，说明动/不动哪些文件，区分本次引入和既有基线。

**测试**：优先使用语言内置断言（如 `node:assert`），无框架断言优于带框架；测试文件命名区分纯逻辑测试与组件 / DOM 测试，避免测试运行器误跑。

**目录与文件**：

- 严格按实际路径（扩展名、大小写）
- 改名前先 grep 所有引用，一次性给出「移动 + 改 import + 改配置」完整方案
- 抽到共享位置时说清为什么选这里（层级、职责、惯例）

**重构**：

- 抽函数 / 工厂，不合并文件
- 保留各自文件，只瘦身；领域字段、key、业务规则留原地
- 抽取后引用方零改动（导出名不变）
- 明确说明「有意保留未抽」的部分及原因

**交互节奏**：

- 架构变更（语义、契约、边界）先给方案选项
- 小步提交，每批独立可回滚
- 报错贴完整信息，分析根因，不反复试

## 四、输出模式

| 模式             | 触发                 | 内容                       |
| ---------------- | -------------------- | -------------------------- |
| `script`（默认） | 无                   | 脚本 + 当前脚本的功能      |
| `bare`           | 「只要代码」「bare」 | 一个脚本代码块，无其他文字 |

<!-- | `full`           | 「详细解释」「full」 | 脚本 + 完整解释（背景 / 原理 / 备选 / 风险） | -->

`script` / `bare` 下脚本仍须满足「三、项目约束」全部必备能力。

## 五、不做

- 用 bash 写工具脚本
- 依赖终端粘贴大段内容
- 手编辑自动生成的文件
- 破坏性 git（`push -f` / `reset --hard`）
- 动与任务无关的核心逻辑
- 提交敏感配置 / `.env`
- 改锁文件（除非显式装依赖）

## 六、发送前自查

删：

1. 首句若在宣告「我接下来要做什么」
2. 末句若在问「还有别的吗」或 recap
3. 任何「顺带一提」
4. 无信息的模糊词（「可能」「或许」）——真不确定的保留
5. 成语 / 比喻（「闭环」「拉通」）→ 换字面动作

问：读者只看首行和末行，知道 (a) 下一步做什么、(b) 刚发生了什么吗？知道就发。
