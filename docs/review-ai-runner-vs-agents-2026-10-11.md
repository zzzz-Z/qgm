## 1. 值得肯定的部分

文档的事实面比同类对比稿扎实得多。特别是 **「65 个方法」这个数字是精确的**——我用脚本解析 `helpers/index.cjs` 的顶层键，实数 65（其中 `lessons` / `tasks` / `browser` 是命名空间，叶子函数 62 个）。这类数字通常来自估算或抄二手资料，能精确命中说明作者真的读了源码。

同理，`browser` 只暴露 `cssom` / `screenshot` 而无 navigate/evaluate、「首问不自动注入技能」这些细节也都与源码逐字吻合。结论部分「AI Runner 的核心优势在于输出契约的确定性和验证的诚实性，借鉴时应优先增强这些优势」——这个判断我认同，它比三条具体建议更有价值。

## 2. 需要更正的部分

### 2.1 一级问题：小标题与自引工单直接矛盾，且小标题那半是错的

第二节标题写 **「AI Runner：每轮注入完整 SYSTEM.md + AGENTS.md + lessons」**，但同一节的「可借鉴之处」里又写：

> WO-20261007-14 已指出「它不是每轮注入，而是每会话/循环首轮一次」

这两句不能同时为真。我查了该工单原文（`docs/archive/workorder-app-system-md-optimization-plan-2026-10-07.md`）：

- **F2（第 34–41 行）**：注入点只有三处——`copyAndFill` 首发送、`buildNewSessionPrompt`（handoff 交接新会话）、`buildLoopInitialPrompt`（循环首轮）。
- 该工单还**点名** `packages/core/tests/system-contract.node-test.ts:2` 里「SYSTEM.md 每轮注入」这句注释**不成立**，并列为待修项 P1-3。

也就是说：文档把一条**已被本仓库判定为错误、且已排队待修的注释**，放大成了一整节的立论前提。

这个错误的代价不小——它直接决定 ROI 排序。若真为「每轮注入」，砍字节就是每轮复利，优先级高；实际是「每会话一次」，则体积不是经常性成本，`prompt-budget` 的真实靶心应是「条文有没有被机器守住」，而非「砍字节」。这正是该工单 F2 的原话。

**改写建议**：小标题改为「首轮全量注入 + 长会话后期规则远离上下文」，并把立论从「体积成本」换成「约束力衰减」——工单第 132 行已经给了后者（50 轮后期规则已在很远处，候选对策是「每 N 轮回传 ≤15 行紧凑摘要」）。

### 2.2 Repo Map 建议：漏掉了已存在的 `__AI__.symbol()`

文档说「当前 AI Runner 的 `grep` + `dump ±20` 是手工版的 Repo Map，可考虑机器化」。方向对，但漏了一个已存在的 API：

- `helpers/search.cjs:92` 有 `symbol(name, opts)`——但读实现（`search.cjs:92-95`）它只是 `new RegExp('\\b' + esc(name) + '\\b')` 后转发给 `grep`，**无 AST、无 PageRank、无相关性排序**。

所以这条建议的正确表述不是「引入 Repo Map 机制」（听起来像从零建），而是「把 `symbol()` 从正则匹配升级为符号级索引」。这个差别决定它被判为「新功能」还是「既有能力增强」——在本仓库的闸门语境下，这个差别直接影响能不能开工（见 §3）。

### 2.3 @verify 建议：`@verify` 已经存在并被解析

文档提议「在 `SCRIPT` 状态中增加一个可选的 `@verify` 指令」。实际上：

- `scripts/verify-contracts.cjs:2` 的 `@desc` 就写着：从 `round-N.json` 抽 `@plan` / `@verify` / `@desc` 声明，与实际 `exitCode` / `pipeline` / `changes` 对比，累积偏差。
- 它已有 `pnpm` 入口：`package.json:61` → `"verify:contracts": "node scripts/verify-contracts.cjs"`。
- 它已经在判两类偏差（`:74-75`）：「声称完成但 exit≠0」「声称验证通过但 exit≠0」。

缺的不是**指令约定**，而是**执行所声明的验证命令**与**把结果标为 `verification-failed`**。这两件事的性质完全不同，见 §3.2。

### 2.4 附赠发现：仓库自身 README 有一处陈旧副本

文档第四节称「没有循环计数、没有硬轮上限」。这条**判为成立**——`packages/client/composables/ai/auto-loop/` 与 `loopLogic.ts` 已整体删除，`LOOP_HARD_MAX_ROUNDS` / `LOOP_HARD_MAX_MS` 全仓零命中，由 `loop-single-path.node-test.ts` 的 `PHASE_VALUE === 'B'` 承重。

但 `README.md:142` 仍写着「硬上限 **50 轮** / **30 分钟**」。这是陈旧副本（工单 WO-20261007-14 第 132 行也仍按「50 轮硬上限」推理，同属过期）。文档作者没被它带偏是对的，但这处不一致本身值得顺手修。

## 3. 三条 P1 建议的可行性判决：全部撞阶段闸门

这是本次复检最实的结论。实测 `bin/check-status.cjs`：

```text
▶ 观察期
· 总 2 条 / 近 14 天 2 条
    manual-copy      0/3  手动复制粘贴烦 -> 阶段 6 API 循环
    style-regress    0/2  改样式改崩没发现 -> 视觉回归
  ! prompt-budget    2/3  prompt 常爆预算 -> 阶段 5 多层级压缩
▶ 结论
✓ 阶段 0 - 3.2 产物到位，阶段 4 观察期就绪
· 规则：>= 2 周不做新功能；仅触发信号达阈值时开下一阶段
```

三条 P1 逐条判：

| 建议           | 判决                                   | 理由                                                                                         |
| :------------- | :------------------------------------- | :------------------------------------------------------------------------------------------- |
| ① Repo Map     | **闸内不可开工，但差 1 条信号**        | 对应阶梯「阶段 5 多层级压缩」，钥匙是 `prompt-budget`，现 **2/3**。                          |
| ② 执行中验证   | **一分为二**：只读对账可做，拦截不可做 | 见下                                                                                         |
| ③ 受限插件机制 | **闸内不可开工**                       | 新增 API 面 + 新增目录约定 = 纯新功能；且它直接削弱文档自己承认的「封闭工具面 = 安全优势」。 |

关于 ② 的拆分，阶段闸门技能的授权边界写得很明确：**「事后对账」类指标（只读既有留痕、不改机制、不拦截）闸内可做；一旦要「拦」或要改行为，就落回需要开闸的那一侧。**

- 可做的半边：扩展 `verify-contracts.cjs` 的对账维度（例如按退出原因分类统计 `anchor-not-found` / `budget-exceeded` / `unstable-output`）——这正是文档第二节末尾提的「命名退出原因」，它是纯只读对账，**今天就能做**。
- 不可做的半边：让 `@verify` 声明的命令真正执行、失败时把结果标成 `verification-failed` 并改变后续流程——这是拦截，需开闸。

补充一个反向证据，关系到 ③ 的成本论证：文档说「工具面固定意味着新能力需要改核心代码」。但 `helpers/index.cjs` 已经是**按族拆分 + 工厂注入**的结构——14 个子文件、`createXxxApi({ self: () => __AI__ })` 装配、新增一族只需加一个 `require` 和一个转发段。「改核心代码」的成本在这里被高估了；真正的成本在**安全面扩张**，不是代码改动量。建议把 ③ 的论证重心从「省事」换成「风险」，否则它通不过评审。

## 4. 方法论层面的四个问题

比事实错误更值得说的是这四条，因为它们会复现：

1. **引用了工单却没采纳工单的结论。** §2 同时出现「每轮注入」与「不是每轮注入」，说明作者读到了 WO 但没让它修改自己的标题。跨轮不复查自己的历史结论，是这类分析最容易犯的错。
2. **提建议前没做「是否撞闸门」的前置核查。** 本仓库把这条门槛放在了 `pnpm session:start` 每会话必显的位置，且 WO-20261007-14 第 133 行已经用同一条理由否掉过一次「首问瘦身」。三条 P1 里两条是新功能，本应先查这里。
3. **建议缺少承重判据。** 按本仓库规矩，任何提案要写明「改恒真后哪个测试会变红」。三条 P1 都没有。例如 ② 若真落地，应指定 `verify-contracts.cjs` 的哪个用例会因「把 `looksLikeVerified` 改成恒真」而变红。
4. **表格里「上下文：每轮全量注入」这一格若按实测更正**，P1 优先级应当下调——不是经常性 token 成本。文档自己在正文里已经引了这个结论，表格却没同步。

## 5. 建议的改写方向

保留文档的骨架与结论（「增强确定性与诚实性，而非盲目追随更自由」这个判断值得留），改这三处：

1. **§2 标题与表格**：把「每轮注入」改为「首轮全量注入」，立论从「体积成本」换成「长会话后期约束力衰减」。同步下调上下文维度的优先级。
2. **三条 P1 各加一行「闸门状态」**：① 差 1 条 `prompt-budget` 信号；② 拆分——命名退出原因的只读对账今天可做，执行+拦截排队；③ 闸内不做，且论证重心改为风险而非省事。
3. **补两条闸内可做的替代项**（比原建议更可能真的落地）：
   - 把 `symbol()` 从正则升级为符号级索引的**可行性调研**（只读、不改行为）——为阶段 5 开闸备料；
   - 扩展 `verify-contracts.cjs` 的退出原因分类统计（纯只读对账）。

另外建议顺手修 `README.md:142` 的陈旧「50 轮硬上限」。
