## 2. 分析一：可行性（Q1 的结论）

### 2.1 四条接入路线

| 路线     | 做法                                   | 惠及谁               | 成本                                                                  | 判定                                                                                                  |
| :------- | :------------------------------------- | :------------------- | :-------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------------- |
| **A**    | `__AI__.wikiSearch()` 沙箱面直连 19828 | 网页端 AI 干活时自查 | 中（新 helpers 子模块 + 三份拷贝清单 + `__AI__` 暴露面 + 集成点判据） | 可行，**但不能带 token**，须走代理                                                                    |
| **B** ⭐ | core 加 `/wiki/*` 代理路由             | 工作台 UI + 沙箱脚本 | **低**（一个 route 文件，照 installer 模式）                          | **推荐基座**：token 只留服务端、无 CORS、可统一超时/降级/留痕                                         |
| **C**    | 宿主侧 MCP（`~/.workbuddy/mcp.json`）  | **只有宿主 AI**      | 极低（分钟级）                                                        | **最快见效**，但应用端一点查不到                                                                      |
| **D**    | 反向：把项目文档导进 wiki 当 sources   | 内容侧而非通道       | 低但**有 SSOT 冲突**                                                  | 谨慎——项目真相归 `docs/` + `SYSTEM.md` + `lessons`，wiki 只能是「外部资料库」，否则变**第四套知识源** |

**推荐组合：B 做基座 + C 做即时便利**（C 今天就能用；B 是可持续的正式通道）。

### 2.2 关键风险：token 边界（唯一的数据泄露面）

沙箱 env 继承（§1.2）意味着：

```js
// AI 脚本在沙箱内可以做到（process 只禁 .exit）
console.log(process.env.LLM_WIKI_TOKEN) // → 进回执 → 渲染到页面上
```

**因此**：token 只能存在于**服务端进程**，由 `/wiki/*` 代理注入 header。
任何「把 token 塞进沙箱 env 或前端」的方案一律否决。

### 2.3 硬前置

1. **LLM Wiki 必须装上并常驻**（GUI 应用，关窗即 API 消失）；
2. 在它设置里**开 API + 生成 token**；
3. 宿主侧 `curl /health` + `/search` 实测打通后，才谈接线。

## 3. 分析二：加成（Q2 的结论）

### 3.1 五个加成（全部有实测数字支撑）

| #     | 加成                                   | 现状痛点（实测）                                                                                                                                                      | 知识库带来的变化                                                   |
| :---- | :------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------- |
| **1** | **把 5% 的利用率拉回正常**（最大加成） | `LESSONS_BUDGET=6000` 且**按尾截断** ⇒ 112 KB / 157 条里只有最后 ~6KB 进上下文；95 条 verified 经验基本不在场                                                         | 语义检索把「相关的 3 条」送进去，而不是「最后写的几条」            |
| **2** | **直接掐掉重复翻案**                   | 7 条 rejected 里有一条「熔断后合法脚本也被 429 拒」，应用端在**三个不同轮次**各写一遍（我标过两次 rejected）——每次都重新推理 + 整轮往返                               | 已判假结论状态化入页 + 生成前检索命中 ⇒ 往返归零                   |
| **3** | **首问从固定开销变可变开销**           | 实测 **39,221 B / 会话**，每次开窗都付，与当轮任务无关                                                                                                                | 改为「静态必读 + 检索 top-k」⇒ 可直接量化节省                      |
| **4** | **终结 memory 的压缩跑步机**           | `.workbuddy/memory` 靠 ratchet（≤4300 字符）与「净零置换」维持，本会话已因超限被压过一次                                                                              | 全量历史放 wiki、按需取片段 ⇒ 压缩从「必须」降级为「可选」         |
| **5** | **代码地图与判据库**                   | 本会话两类误判都是「知道得不够」：宿主侧**查错目录**（`packages/core/dist` vs `apps/standalone/dist`）误判 build 未跑；应用端 `__AI__` 面**漏暴露**两个方法却测试全绿 | 模块→责任→判据 的页面 + 判据真空形态/变异协议索引 ⇒ 少犯错、少返工 |

### 3.2 一个反向加成（容易被忽略）

`POST /pages/embed` 支持**外部生成页面直接入库** ⇒ auto-loop 每轮结论可**自动沉淀为 wiki 页**，
写入摩擦远低于现在手工 `lessons:add`（本会话 pending 已积到 **49 条 / 31.2%**，略超 ratchet 30% 线）。
知识资产从「人工记账」变为「自动生长」。

### 3.3 必须配的三条纪律（否则反噬）

1. **wiki 只作线索，事实以磁盘 / 活端点为权威**——与项目既有的「运行时 ≠ 源码」同一纪律；过期页会把错误放大；
2. **已否决状态必须随条目入页**——否则 wiki 会把判假结论当事实喂回去，正好放大 §3.1 第 2 条的旧坑；
3. **SSOT 不迁移**——`docs/` + `SYSTEM.md` 仍是唯一权威，wiki 只做索引与蒸馏。

### 3.4 优先级（加成排序）

**lessons 检索化 > 首问瘦身 > 已否决结论前置拦截 > 代码地图/判据库 > 外部资料检索**

## 4. 实施计划

> 分工总则：**阶段 0 只能用户做**（GUI）；**阶段 1–3 由应用端实施，宿主侧出工单 + 复检 + build/restart**；
> 本计划的落地形式是**一张直派工单**（**已派发：`WO-20261007-08`**，落
> `docs/workorder-app-kb-integration-2026-10-07.md`），不把本文件当工单用。
> 编号注：06/07 已被应用端自拟工单占用，故顺延 08。

### 阶段 0 — 打通外部依赖（用户，~10 分钟）

| 项     | 内容                                                                                                           |
| :----- | :------------------------------------------------------------------------------------------------------------- |
| 动作   | 安装 LLM Wiki → 建一个项目 → 设置里开 API + 生成 token → 把 `URL` / `token` 告知宿主侧（或自行写入服务端 env） |
| 交付物 | `curl http://127.0.0.1:19828/api/v1/health` 返回非错误；宿主侧实测 `/search` 有结果                            |
| 判据   | **宿主侧亲跑**（不采信自述）：`/health` 200 + `/search?q=lessons` 返回结构含结果数组                           |
| 阻塞   | 未完成则阶段 1 无法验收（假 wiki stub 可代跑，但真实联通必须验一次）                                           |

### 阶段 1 — core `/wiki/*` 代理路由（P0，基座）

| 项           | 内容                                                                                                                                                                                                                                                                                                                                          |
| :----------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 落点         | 新增 `packages/core/src/routes/wiki.ts`，挂进 core 路由表；env `LLM_WIKI_URL`（默认 `http://127.0.0.1:19828`）、`LLM_WIKI_TOKEN`                                                                                                                                                                                                              |
| 端点         | `GET /wiki/health`、`GET /wiki/search?q=&limit=`；**token 只在服务端 header 注入**                                                                                                                                                                                                                                                            |
| 超时         | 3s（`AbortSignal.timeout`），失败**显式降级**                                                                                                                                                                                                                                                                                                 |
| 留痕         | 复用 `control-log` 记录调用（q 摘要 + 命中数 + 耗时），**不记 token**                                                                                                                                                                                                                                                                         |
| 判据（承重） | ① **假 wiki stub（本地起 19828 替身）**：`/wiki/search` 返回结果；**变异**：去掉 token header ⇒ stub 返 401 ⇒ 判据**变红**（证 token 真被注入）；② **stub 被杀**：返回 `{ degraded: true, reason }` 且 HTTP 200，**不是** `{ results: [] }`；**变异**：把降级分支改成返回空数组 ⇒ **变红**；③ **响应体与日志不含 token 字面量**（字符串断言） |
| 反例提示     | ③ 若只在「成功路径」断言，等于判据真空——须在**失败路径**也断言不回显                                                                                                                                                                                                                                                                          |

### 阶段 2 — 工作台入口（P1）

| 项   | 内容                                                                                                                                     |
| :--- | :--------------------------------------------------------------------------------------------------------------------------------------- |
| 落点 | 工作台加「知识库」面板：`/wiki/health` 探活显示**在线 / 离线（降级原因）**；一个只读搜索框（显示命中条目的**文件路径**，不直接注入对话） |
| 判据 | wiki 在线 ⇒ 显示在线且搜索有结果；wiki 离线 ⇒ 显示「离线下线」而非空列表；**变异**：把离线态也渲染成空列表 ⇒ 变红                        |
| 约束 | 先**只读**，不做「一键注入对话」（避免污染上下文，待观察）                                                                               |

### 阶段 3 — 给网页端 AI 的检索面（P2）

| 项                  | 内容                                                                                                                                                                                                                 |
| :------------------ | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 两个选项            | **(a) 薄封装**：`__AI__.wikiSearch(q, limit)`，内部 fetch `http://127.0.0.1:5175/wiki/search`；**(b) 不加 API**：仅在提示词/技能里写明「可直接 `fetch('http://127.0.0.1:5175/wiki/search?q=...')`」                  |
| 推荐                | **(a)**——可统一超时/限流/降级/留痕；代价是要付 §「WO-04 教训」的账                                                                                                                                                   |
| 硬要求              | 若选 (a)：**必须补「经 `__AI__` 面」的承重判据**（vm/require 后走 `global.__AI__.wikiSearch` 断言生效）——WO-04 刚踩过「模块测过了但 `__AI__` 面漏暴露、测试全绿」的坑；**变异**：删掉 `__AI__` 面的转发行 ⇒ 判据变红 |
| 若选 (a) 的额外成本 | 新 `.cjs` 不是必须（可内联进 helpers-io.cjs）——但 helpers.cjs 已拆过一轮，新增前先看 `module-size-ratchet` 是否越线                                                                                                  |

### 阶段 4 — 可选：宿主侧 MCP（C 路线）

给 `~/.workbuddy/mcp.json` 加 LLM Wiki 的 MCP server 条目，让宿主 AI 也能直接查。**与阶段 1 不冲突**，可随时做。

### 4.1 明确不做

- ❌ **不给沙箱开通用 fetch 能力包**——它本来就能 fetch（禁令不拦），但**不额外提供任何把外部数据自动写回项目/回传页面的通道**，避免形成数据外泄面；
- ❌ **不把项目文档镜像进 wiki**（D 路线的 SSOT 冲突）；
- ❌ **不把 token 放入前端或沙箱 env**；
- ❌ **不做「一键把检索结果注入当前对话」**——首问/上下文污染风险，待阶段 2 观察后再议。

### 4.2 执行顺序与依赖

```text
阶段 0（用户）──┐
                ├─→ 阶段 1（基座）─→ 阶段 2（UI）─→ 阶段 3（AI 面）
                └─→ 阶段 4（MCP，可并行）
```

## 8. 附：本文档的论证边界（诚实标注）

  阶段 0 的宿主侧 `/health` + `/search` 是第一次真实校验，可能推翻本文对端点形状的假设；
- 若阶段 0 发现 API 形状与假设不符，阶段 1 的判据须按实际响应结构调整，本文件相应更新。
