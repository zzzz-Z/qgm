## 段八 · 自复检留痕（2026-10-10 02:0x–02:1x）

### C1 · 硬伤（已撤回）：段四 v1 的「handoff 是现役链路」

- 原判据：`handleSummaryMsg` **无条件**调用 `autoLoop.onSummary` ⇒ 推断为现役。
- 实测：`onSummary` 内部第一行就 `state !== 'handoff'` 早退，且该状态不可达；叠加
  「无发送方 + 无订阅方」两重证据 ⇒ 结论**完全反转**（见段四）。
- 归因（教训）：v1 只读了**调用点**，没读**被调用函数的守卫**，也没查**消息类型是否真有人发**。
  判「某条链是否活着」必须三查：调用点 + 被调函数入口守卫 + 消息/事件的发送方存在性。

### C2 · 判据真空（已加固）：P0 的「零调用点」是空结果形态

### E2 · 环境缺陷（实测；独立于本计划，值得单开一轮修）

1. **代理目标失配**（实证）：同一路径 `/__ai/preset/system` ——
   经 **5174 代理 = 502**；直连 **5175 = 200**；直连 **5519 = 400**（后端本身健康）。
   ⇒ 复用的前端实例与本轮后端**不是同一套**。
2. **`.server-port` 在运行中被反复改写**：02:18 读数 `5519`；02:23:48（运行刚结束）变回 `5175`。
   机制（**推断**，未直接取证）：`vite.config.ts resolveBackend()` 在**配置加载时一次性求值**
   （env `AIR_BACKEND_URL` > `.ai-runner/.server-port` > 5175），复用中的旧前端**不会重读**该文件；
   而 spec 的 `beforeAll` 各自拉起后端并改写它 ⇒ 复用旧前端必然打旧目标。
   **旁证**：本项目日志自陈，上一轮跑同一 spec 时曾显式指定 `AIR_BACKEND_URL=http://127.0.0.1:5519`
   （且「各 spec 自起 server 端口不同（5518 / 5519）」）—— 若那次运行期间由 Playwright 自启了 dev server，
   该前端的代理目标就被 `AIR_BACKEND_URL` **永久冻结**在一个随后会消失的临时端口上
   ⇒ 之后每次复用它都必然 502。（冻结的具体端口**未取证**：5174 进程已亡，`ps` 被宿主拦。）
   与 `playwright.config.ts` 自陈一致：「后端由具体 spec 的 beforeAll 独立拉起」，
   且 webServer `url: 'http://localhost:5174/'` **只探前端、不探后端** ⇒ 代理失配不会被探活拦住。
3. **5174 中途死亡**：运行结束后 5174 无监听。归属**未定**（无法取证：`ps` 被宿主拦且进程已亡）——
   可能是复用到的旧实例自然死亡，也可能是 Playwright 自启后在 teardown 回收，本轮无法区分。

⇒ 要拿干净基线：先清掉 5174 上的旧实例与 `.server-port` 残留，再跑（`.server-port` 若留着死端口，新实例会照旧 502）。

`headless-ws.spec.ts` spawn 传该开关）。**前半属实、后半不全**，逐条取证：
