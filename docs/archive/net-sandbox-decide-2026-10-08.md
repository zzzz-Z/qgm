# [net-sandbox-decide] 「沙箱内后台进程访问不了 10.61.129.66:8088」判决

日期：2026-10-08 20:20 · 判决方：宿主侧 · 结论：**前提不成立（网络层无障碍），真实差异在「进程生命周期」层；暂不需要宿主侧改网络策略，也不需要另给后端地址。**

---

## 1. 判决一句话

宿主侧沙箱**没有**「前台能连、后台不能连」的出网策略差异：同一个目标、同一个命令，前台、`nohup &`、托管后台任务、`setsid` 孤儿都能拿到 `200`。
真正会导致「后台那一侧连不上」的是：普通后台进程**在工具调用返回时被回收**，后续「打服务」打到的是一个**已经不存在的进程**——现象很像网络不通，实则是进程没了。

## 2. 实测证据（本机·宿主侧 Bash 沙箱）

环境事实：本机 `en7 = 10.61.129.57/24`，网关 `10.61.129.1` ⇒ 目标 `10.61.129.66` 是**同二层邻居**，不需要 VPN；
`HTTP(S)_PROXY=127.0.0.1:57792` 由沙箱控制进程（`sandbox-c…`，pid 77334）持有。

| #   | 进程形态                            | 存活跨调用 | `curl http://10.61.129.66:8088/`                                       | 备注                                                     |
| --- | ----------------------------------- | ---------- | ---------------------------------------------------------------------- | -------------------------------------------------------- |
| E1  | 前台（继承代理 env）                | —          | `200`（走 `127.0.0.1:57792`）；禁代理也 `200`（`remote=10.61.129.66`） | 直连/代理双通                                            |
| E2  | `nohup … &`（同一调用内）           | 调用内     | `200`                                                                  | **调用一返回即被回收**：心跳日志只剩首行，`18099` 无监听 |
| E3  | 托管后台任务（`run_in_background`） | ✅         | 18/18 `direct=200`，跨 4 个工具调用持续                                | 任务自身结束才退出                                       |
| E4  | `setsid` 双 fork 孤儿（ppid=1）     | ✅         | 连续 19+ 条 `direct=200`，跨多调用持续 ≥90s                            | Python `os.setsid()` 两跳 `fork`                         |
| E5  | 孤儿 HTTP 服务 `127.0.0.1:18100`    | ✅         | 后续调用 `curl` 得 `{"ok":true,"via":"upstream=200"}`                  | 服务**自身**出网也通                                     |
| E6  | 绑 `0.0.0.0:18101` 并用 LAN IP 访问 | —          | `loopback=200 lanip=200`                                               | bind 到非回环也放行                                      |
| E7  | `env -i` 剥环境后直连**公网**       | —          | `200`（`104.20.23.154`）                                               | 沙箱连公网都不拦 ⇒ 不存在出站白名单之差                  |

> 复现脚本留在 `/tmp/netprobe/`（`probe.sh` / `longprobe.sh` / `longbg.sh` / `orphan.py` / `srv.js` / `serve-orphan.py`），任何人可重跑。

## 3. 三个候选解释的排队（按验后可信度）

1. **C1 生命周期（已证实，唯一站得住的）**：普通后台作业随工具调用被回收。
   判据：E2 日志在调用返回瞬间断尾 + 端口无监听；对比 E3/E4 同一套 curl 逻辑改用其它存活方式即全绿。
2. **C2 代理服务器（已排除）**：`env -i` 剥掉 proxy env 后，直连公网 E7 仍 `200` ⇒ 代理不是唯一出口；
   且 E1 证明该 LAN 目标连代理都不需要。
3. **C3 真·网络策略差异（已否）**：沙箱出站无限制（E7），且若能拦，前台（E1）必一起被拦，不会出现「只拦后台」。

> 附带提醒：`fail-fast` 的三类判据不同——`exit 7/ECONNREFUSED`（没人听＝进程没了或被地址拒绝）、
> `exit 28/timeout`（可能被拦或路由不通）、`进程已不在 ps`（纯生命周期）。**先 errno 二分，再谈网络策略。**

## 4. 对两个提议的处理

- **提议 A「宿主侧调整网络策略」**：❌ 暂不需要。没有策略在被触发（E1+E3+E4+E7 已证同一目标多形态全通），
  改了也不会让 v 现象消失——因为它不是网络现象。**先要一条同一时刻、同一目标、同一命令的最小复现**再谈改策略。
- **提议 B「提供沙箱内可达的后端地址」**：❌ 对当前目标无必要（`10.61.129.66` 本就可达）。
  ⚠️ 但有一个**变体保留**：若失败方其实在**容器/远端**里（本项目 `compose.yaml` 是默认 bridge，出网走 NAT，
  通常可达 10.61.x；若将来换 `network_mode: none` 或跨命名空间就不一定），那时的正解是
  `network_mode: host` 或宿主侧 loopback 端口转发（`ssh -L` / socat 把远端映射成 `127.0.0.1:<P>`），
  而不是改宿主网络策略。

## 5. 推荐动作（按成本从低到高）

1. **改起法，不改网络**：需要在沙箱内「起服务再打服务」时，用 `setsid` 双 fork 孤儿（E4/E5 范式）
   或托管后台任务（E3）；长稳服务继续用 pm2（已验证可跨会话存活，且应用端不能 kill 承载会话的进程）。
2. **强制留证据再上报**：复现时附三件套——
   `lsof -nP -iTCP:<P> -sTCP:LISTEN`（有没有在听）、`/bin/ps -p <pid> -o pid,ppid,lstart=`（活着吗、谁生的）、
   `curl -sS --noproxy '*' -m 5 -o /dev/null -w '%{http_code}\n'` + 退出码（7 / 28 / 二分类）。
   缺这三件，「网络策略」结论一律记为 `degraded`。
3. **只有当**「进程存活 + errno=28/超时 + 前台同刻成功」三者同时成立，才真的进入 A/B 路线。

## 6. 记忆修订（覆盖旧结论）

- 旧：`pm2 必须免沙箱，沙箱内守护活不了`。
- 新：`&` / `nohup &` 后台进程**随工具调用被回收**；`setsid` 双 fork 孤儿与托管后台任务**可跨调用存活且出网正常**；
  pm2 仍推荐（跨会话、自动拉起），但理由从「沙箱跑不了守护」改为「托管更稳」。
