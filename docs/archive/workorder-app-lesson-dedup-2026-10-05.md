## 背景：本轮冒出的新缺陷，是宿主侧在复核你 DONE 时撞见的

你的 `DONE` 里 `## 踩坑记录` 有 3 条。服务端按既有机制把它们**自动采集**并追加进了 `.ai-runner/lessons.md`
（采集时刻 20:09:52）。追加之后，**`lessons-hygiene` 守卫当场变红**：

```text
× 无近重复标题（归一化二元组 Jaccard ≥ 0.35 即视为同族残留）

0.41  「`docs/plan/**` 在 `.gitignore` 里但不在 eslint `ignores` 里」 ↔
      「`docs/plan/**` 在 `.gitignore` 里 `@antfu/eslint-config` 会自动忽略，但 `LINT_SKIP_SEGMENTS` 不会」
```

**这不是你的错**：你的 DONE 完全合规、踩坑记录也写得有价值，是我上一轮该标记的近重复来源被采集侧放行了。
但它暴露出一个**机制缺口**，而且是本质的：

- **采集侧**（`packages/core/src/post-run/lesson-extract.ts:192-204`，`[lesson-dedup-norm-v1]`）判定重复用
  **归一化后完全相等**（`seen.has(norm(title))`，只去空白/反引号/标点后比相等）；
- **守卫侧**（`packages/core/tests/lessons-hygiene.node-test.ts:86-100`）判定重复用
  **归一化二元组 Jaccard ≥ 0.35**（`normTitle` 只留 `a-z0-9` 与 CJK，再比字符二元组相似度）。

⇒ 同一个「重复」概念，两侧是**两套口径**：宽的那套在**写入侧**，严的那套在**闸门侧**。
于是写入方按自己的口径完全合规，却能合法地写出一个**立刻让 `pnpm verify` 变红**的状态。
这与本项目已有的教训（「内联常量必须同构」——同一份判定刻意多写一份，改一处必须全处同步）**同源**。

宿主侧已做的即时处置（见段四，供你对账，勿复述为你的结论）：把那条近重复条目并入 SSOT 并删除、守卫复绿。

## 段一：给写入侧加「不低于闸门」的近重复判定（核心，必做）

**现状必须由你亲自核实**（不要采信本节的转述）：读 `lesson-extract.ts` 的去重段与守卫的近重复用例，
确认两侧口径分别是「相等」与「相似度 ≥ 0.35」。

**要求**：

1. 写入侧（`appendLessons`）在落盘前，把待追加标题与台账**现有标题**做近重复比对；
   命中者**不新增条目**，改为**并入既有条目**——在该条目正文末尾追加一行
   `补充（<日期>）：<被采集的正文>`。**不要静默丢弃内容**：内容丢失与静默吞掉是同一类缺陷。
2. **写入侧判定必须不低于闸门侧**（即：闸门判红的，写入侧必须已拦住）。二选一，并说明理由：
   - **同源（首选）**：把 `normTitle` / `bigrams` / `jaccard` / 阈值抽成**单一实现**的共享模块，
     写入侧与守卫侧都从它导入（消除「两套口径」本身）。抽模块时注意 ESM 的 `.js` 后缀导入约定；
   - **等价性守卫**：保留两份实现，但新增一条测试断言「两侧的归一化与阈值一致」，
     且构造一个**恰好落在两口径之间**的标题（如本轮这条 Jaccard 0.41、归一化不相等），
     证明写入侧确实拦得住。
3. **可观测**：被判定为近重复而并入的条目，必须在采集返回值或日志里留下可观测痕迹
   （例如 `appendLessons` 的返回值扩展，或 `__AI__.log`）。
   `[WHY]` 静默改变行为且无从察觉，与 D8「降级不可观测」是同一族缺陷。
4. **先红后绿，且红要可复现**：
   - 先构造一个**含近重复踩坑标题**的 DONE 文本 → 走采集 → 断言守卫**变红**（贴原始输出）；
   - 改完后同一构造 → 断言**不新增**、守卫**保持绿**（贴原始输出）。
5. **承重判据**：做一次变异（把写作侧阈值调成恒不命中，例如阈值改 `1.0`），
   **第 4 步的断言必须变红**。若不变红，说明判据是真空的 —— 这比不写还危险。
6. 改动 `packages/core/src/**` 后**必须**跑：`pnpm test:tsc`（测试环境没有 auto-import 插件）、
   `pnpm tsc`、以及 `packages/core/tests/post-run-lesson-extract.node-test.ts` 与
   `packages/core/tests/lessons-hygiene.node-test.ts`。

**边界**：`lessons-hygiene` 的阈值 `0.35` 是 ratchet（收紧只会让新条目更难通过）。
**不要放宽它**来绕过红灯 —— 放宽阈值等于把闸门关掉，属掩盖而非修复。

## 段二：修报告里会即刻腐化的数字（必做）

`docs/defect-review-verification.md` §十三 段一引用了一组计数：
`git diff --numstat` = `58 0`、`wc -l` = 644、`新增 6 条台账条目`。

**这三个数在你写下它们的那一刻是准确的**（宿主侧核对过），但**在你交付之后就被改掉了**——
被改的原因恰恰是**你自己那份 DONE 的踩坑记录**被自动采集追加：

```text
现在（宿主侧亲跑）：git diff --numstat → 70  0     wc -l → 656     新增 ## 条目 → 9 条
差额：+12 行 / +3 条 = 你那 3 条踩坑记录被采集进来的量
```

**要求**：

1. 把这些数字改述为**不依赖快照**的表述（例如「相对 HEAD 只显示新增、删除列为 0」），
   或明确标注为「测量时刻快照 + 给出重跑命令」。
2. 在 §十三 顶部加一句：「本报告所有计数为快照，复核时以命令重跑为准。」
3. `[WHY]` 这是本轮两轮工单里第 5 次「计数类断言被推翻」（前 4 次：url-parse 四处→五处、
   遮罩 3 条→7 条、Content-Length 主路径、lessons「删除」）。
   **根因不是粗心，是计数类断言的系统性衰减** —— 每一条都在文档写下的瞬间开始过期。

## 段三：给自己报告做一次「计数类断言总账」（必做）

通读 `docs/defect-review-verification.md`，把其中**所有**形如「N 处 / N 条 / N 行 / N% / N 个」
的断言列成一张清单，逐条给出：**断言原文 → 位置 → 重跑命令 → 当前值 → 是否仍成立**。

- 不一致的：当场改述，并标注「已过时（改述）」；
- 一致但脆弱的：标注「快照，易腐化」；
- **报告里不许留无命令可复现的计数**。

`[WHY]` 这一步的收益是把「报告状态过时」从「靠复核方一个个抓」变成「自己有一张可重跑的账」——
前两轮的返工基本都花在这上面。
