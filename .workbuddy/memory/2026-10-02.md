## 第二轮：重启循环 bug 修复 + 登录窗口实测打通

### 自己引入的 bug（已修复，教训重要）

- **容器 restart 会保留 `/tmp`**：上一轮的 `/tmp/.X99-lock` 和 `/tmp/.X11-unix/X99` 还在，
  Xvfb 以 `Server is already active for display 99` 退出；而等待循环只检查 socket 文件存在 → 立即误判就绪；
  `set -e` 让 entrypoint 退出 1 → `restart: unless-stopped` 放大成无限重启循环（11 次 restarts）
- 修复：entrypoint 启动前 `rm -f /tmp/.X99-lock /tmp/.X11-unix/X99`；等待循环同时校验
  `kill -0 $XVFB_PID`；x11vnc/openbox 全部 `|| echo 警告` 降级，绝不让 X 栈失败拖垮主服务
- **验证方法（好用，值得复用）**：不用重建镜像，`docker run -d --name t -v ./docker-entrypoint.sh:/usr/local/bin/docker-entrypoint.sh:ro qgm/ai-runner:local sleep 600`
  然后 `docker restart t` 两轮，即可在秒级内验证 entrypoint 的冷启 + restart 两条路径
- 教训：**给 `restart: unless-stopped` 的服务写 entrypoint，任何一步都必须容错降级**，
  否则启动失败 = 无限重启循环

### 僵尸进程坑（本次排查的第二个真凶）

- `pkill chrome` 这类硬杀会让 chrome 变 `<defunct>` 僵尸；僵尸直到父进程(PID 1)回收前都存在，
  `kill(pid,0)` 返回成功 → Chromium 的 stale-lock 检查误判「profile 被占用」→ 启动即退，
  报错同样是 `Target page, context or browser has been closed`
- **正确恢复方式：`docker compose restart`**（杀掉整棵进程树即清僵尸，entrypoint 再清 Singleton*）
- 禁止对容器内浏览器用 `pkill chrome`；要关窗口/会话走应用自己的 WS 帧或重启容器

### 无头端到端实测（15:15–15:28，全链路打通）
